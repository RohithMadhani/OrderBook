# Low-Latency Order Book

A C++20 low-latency order book and market-data processing pipeline designed around an event-driven architecture.

The project processes an ITCH-style market-data feed, converts incoming messages into normalized events, passes them through a low-latency queue, and applies them to an in-memory order book.

---

## Pipeline

```text
                    ITCH Market Data
                           │
                           ▼
                  Memory-Mapped Input
                           │
                           ▼
                     ITCH Parser
                           │
                           ▼
                  Event Normalization
                           │
                           ▼
                    SPSC Event Queue
                           │
                           ▼
                      Order Book
                           │
                           ▼
                 Matching / Book State
                           │
                           ▼
              Performance Measurements
```

### 1. Market Data Input

The pipeline starts with a binary market-data file containing ITCH-style messages.

The feed can contain messages belonging to multiple instruments.

A target instrument can be selected when running the benchmark.

---

### 2. Memory-Mapped Input

The market-data file is memory-mapped before processing.

This allows the parser to access the feed directly through the process's virtual address space and avoids repeatedly performing explicit file reads during message processing.

The mapping is prepared before the benchmark pipeline starts so that file-access overhead has less impact on the measured processing path.

---

### 3. ITCH Parser

The parser processes the binary feed sequentially.

It:

- Reads individual messages from the feed.
- Identifies the instrument associated with each message.
- Filters messages for the requested instrument.
- Converts relevant messages into internal market events.

The parser handles the main order lifecycle events:

- Add
- Execute
- Cancel
- Delete
- Replace

The result is a stream of normalized events that can be consumed by the order book.

---

### 4. Event Queue

Parsed events are passed from the producer side to the order-book processing side through a bounded SPSC queue.

```text
Parser
  │
  │ events
  ▼
┌──────────────────┐
│   SPSC Queue     │
└──────────────────┘
  │
  │ events
  ▼
Order Book
```

The producer and consumer operate independently, allowing market-data parsing and order-book processing to run concurrently.

The queue is designed specifically for a single producer and a single consumer and uses cache-conscious synchronization.

---

### 5. Order Book

The order book maintains the current state of the selected instrument.

It processes the normalized events generated by the parser and maintains:

- Buy-side orders
- Sell-side orders
- Price levels
- Order quantities
- Order priority
- Best bid
- Best ask

Orders at the same price follow price-time priority.

The order book also supports order matching and keeps track of executed trades.

---

### 6. Performance Measurement

The pipeline includes performance measurement for both individual order-book operations and the complete processing path.

The benchmark reports latency statistics such as:

- Mean
- P50
- P90
- P99
- P99.9
- Maximum

It also reports overall event-processing throughput.

A latency histogram can be used to visualize the distribution of processing times.

---

# Synthetic Market Data

The project includes a synthetic ITCH feed generator for creating reproducible workloads.

The generated feed contains multiple instruments and a mixture of realistic order lifecycle events, including:

- New orders
- Partial cancellations
- Full cancellations
- Partial executions
- Full executions
- Order replacements

The generator also maintains the expected state of the generated orders, allowing the final order-book state to be verified against the generated workload.

---

# Requirements

- Linux / WSL
- C++20-compatible compiler
- CMake
- POSIX threading support

The project is primarily intended to run in a Linux environment.

---

# Build

From the project root:

```text
cmake -S . -B build
cmake --build build
```

Run the test suite with:

```text
ctest --test-dir build --output-on-failure
```

---

# Generate Market Data

The synthetic feed generator can be used to create a workload:

```text
./build/gen_itch <output_file> [number_of_messages] [seed]
```

For example:

```text
./build/gen_itch market.itch 2000000 1
```

This generates a two-million-message workload using a fixed seed.

Using the same seed makes the generated workload reproducible.

---

# Run the Benchmark

The main benchmark is run using:

```text
./build/bench <itch_file>
```

For example:

```text
./build/bench market.itch
```

By default, the benchmark processes the configured default instrument.

---

## Select an Instrument

A different instrument can be selected using:

```text
--symbol
```

Example:

```text
./build/bench market.itch --symbol AAPL
```

---

## Control Input Rate

The benchmark can optionally process events at a specified target rate:

```text
--rate
```

For example:

```text
./build/bench market.itch --rate 1000000
```

This allows the pipeline to be tested under a controlled event rate.

---

## CPU Pinning

The producer and consumer threads can be assigned to specific logical CPUs:

```text
--pcpu
--ccpu
```

Example:

```text
./build/bench market.itch --pcpu 2 --ccpu 4
```

This can be useful when evaluating latency and throughput under controlled CPU placement.

---

## Save Latency Data

Latency samples can be exported to a CSV file:

```text
./build/bench market.itch --csv latency.csv
```

---

## Save an Order-Book Snapshot

A final order-book snapshot can be written to a file:

```text
./build/bench market.itch --snapshot snapshot.txt
```

---

# Example Full Run

A complete workflow can look like:

```text
cmake -S . -B build
cmake --build build

ctest --test-dir build --output-on-failure

./build/gen_itch market.itch 2000000 1

./build/bench market.itch \
    --symbol AAPL \
    --rate 1000000 \
    --pcpu 2 \
    --ccpu 4 \
    --csv latency.csv \
    --snapshot snapshot.txt
```

The resulting benchmark provides:

- Number of processed events
- Processing throughput
- Order-book operation latency
- End-to-end latency
- Latency percentiles
- Latency distribution
- Number of successful/failed book operations
- Number of matched trades
- Final order-book state

---

# System Overview

The complete system can be viewed as five major stages:

```text
┌───────────────────┐
│   Market Data     │
│   ITCH Feed       │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Memory-Mapped     │
│ Input             │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ ITCH Parser       │
│ + Instrument      │
│   Filtering       │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ SPSC Event Queue  │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Order Book        │
│ + Matching        │
│ + Book State      │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│ Benchmark &       │
│ Latency Metrics   │
└───────────────────┘
```

The architecture separates **market-data ingestion**, **event transport**, and **order-book processing**, making it possible to measure each stage as well as the complete end-to-end pipeline.
